# AGENTS.md

Guidance for AI coding agents working in this repository. `CLAUDE.md` and `AGENTS.md` are identical mirrors of each other (only the title differs); when you change one, apply the same change to the other.

## Project Overview

`Behind Every Wall` (repo name `BehindTheWalls`) is a Roblox horror game synced through Rojo. The source of truth for scripts, module code, generated networking code, and explicitly Rojo-owned JSON-backed instances is under `src`, with the Roblox hierarchy defined by `default.project.json`. Everything else in the place file (map, UI templates, `StarterGui`, `Workspace`) is Studio-owned and edited through Roblox Studio.

The experience has two places, the lobby (`118916171408858`) and the actual game place (`115970043416367`), and both are built from the single `default.project.json` tree. Place ids live in `src/replicatedFirst/PlaceIds.luau` (exposed as `Config.Places` and `Config.isGamePlace()`), and the registries and `ReplicatedFirst` scripts pick their behavior from `game.PlaceId` at runtime. Only the lobby runs the loading screen, intro, menu, and party flow; the game place runs the systems and controllers under `src/game`, which the tree mounts as the `Game` subfolders of `Systems` and `Controllers`.

The architecture mirrors the `Me-OW!` skeleton (`../Me-OW`): ProfileStore persistence, Replica replication, Blink networking, and the system/controller registry pattern.

This file applies to the entire repository.

## Source of Truth Rules

- Never edit script source inside Roblox Studio (directly or through Studio MCP tools). Edit the files on disk and let Rojo sync them in.
- Roblox Studio MCP tools, when connected, are for read-only inspection and runtime verification only.
- Use Rojo/Git for scripts, modules, and generated networking code. Use Roblox Studio for map/building/UI edits unless the asset is explicitly represented in `src`.
- The intro loading screen (`ReplicatedFirst.Loading_Handler` and its `LoadingScreen` GUI) is Rojo-owned: the script is `src/replicatedFirst/Loading_Handler/init.client.luau` and the GUI is `src/replicatedFirst/Loading_Handler/LoadingScreen.model.json`.
- Do not commit generated `.rbxl`, `.rbxlx`, `.rbxm`, or `.rbxmx` files.
- `sourcemap.json` is a generated artifact, not hand-maintained source.

## Repository Layout

- `src/server/Bootstrap.server.luau` is the server entry point; it starts `SystemRegistry`.
- `src/server/Systems` contains server systems started by `SystemRegistry` (`DataSystem`, `SpawnSystem`, `PartySystem`). `SystemRegistry` starts `DataSystem` everywhere, then either the lobby systems or the game systems from `Systems.Game` depending on `Config.isGamePlace()`.
- `src/server/Modules` contains server-only services and helpers (`DataService`, `ProfileTemplate`, `ProfileStore`, `DataConfig`).
- `src/client/Bootstrap.client.luau` is the client entry point; it starts `ControllerRegistry`.
- `src/client/Controllers` contains client controllers started by `ControllerRegistry` (`PlayerDataController`, `IntroController`, `MusicController`, `FootstepsController`, `MenuButtonsController`, `PartyController`, `TeleportHudController`). In the game place `ControllerRegistry` starts only `PlayerDataController`, `FootstepsController`, `TeleportHudController`, `Controllers.Game.FirstPersonCameraController`, `Controllers.Game.CutsceneController`, and `Controllers.Game.FlashlightController`.
- `StarterGui.MenuPanels` (the Shop/Index/Badges/Settings panel frames) is Studio-owned; `MenuButtonsController` finds panels by name (`ShopFrame`, `IndexFrame`, `BadgesFrame`, `SettingsFrame`) and any button named `Exit`/`Close` inside a panel closes it.
- `StarterGui.PartyGui` (the portal party/queue screen) is Studio-owned; `PartyController` drives it by child names (`Panel`, `SizeRow.Size_1..6`, `DifficultyRow.Easy/Normal/Hard`, `FriendsRow.FriendsToggle`, `MembersLabel`, `StartButton`, `LeaveButton`, `Toast`). The server side is `PartySystem`, which owns the `Workspace.Portal` portals, their `BORDER` touch walls, `TELEPORT` pads, and billboard text.
- `StarterGui.Teleporting_HUD` (the full-screen teleport/loading overlay) is Studio-owned in the lobby; `TeleportHudController` drives it by child names (`Outer_Frame`, `TextLabel`). It is shared by both places: in the lobby it fades the HUD in on `PartyTeleporting`, registers it with `TeleportService:SetTeleportGui`, and acks with `PartyTeleportReady`; it turns CoreGui off whenever the HUD is shown (re-enabling it on hide only in the lobby, since `CutsceneController` owns that in the game place); in the game place it picks up the arriving copy and shows `Loading Players... [arrived/expected]` from `ArrivalState` until the match gate opens, then holds for `Config.Party.MinLoadingSeconds` and the `CutscenePreloaded` attribute (up to `Config.Party.PreloadTimeoutSeconds`) before setting the `ArrivalComplete` player attribute and fading out.
- `src/client/Modules` contains client-only modules (`IntroScene` owns the sewer intro scene effects), synced to `StarterPlayerScripts.Client.Modules`.
- `src/shared/Modules` contains modules shared by client and server (`Config`, `GameInfo`), synced to `ReplicatedStorage.Shared.Modules`.
- `src/replicatedFirst/Loading_Handler` is the `ReplicatedFirst` intro/loading screen (script plus JSON-backed GUI); it returns immediately in the game place. `src/replicatedFirst/PlaceIds.luau` is synced to `ReplicatedFirst.PlaceIds` so `ReplicatedFirst` scripts can check the place before `ReplicatedStorage` is available.
- `src/network/main.blink` is the Blink IDL source.
- `src/shared/Blink/Client.luau` and `src/shared/Blink/Server.luau` are generated by Blink. Do not hand-edit them.
- `src/vendor` contains vendored dependencies (Replica, and `WRagdoll`, the R15 ragdoll module mounted at `ReplicatedStorage.WRagdoll`). Avoid modifying vendor code unless the task explicitly requires it.
- `src/server/Modules/ProfileStore.luau` is vendored ProfileStore. Treat it like vendor code.
- `src/game/server/Systems` holds the game place server systems (`MatchSystem`, `GameSpawnSystem`, `FlashlightSystem`), mounted at `ServerScriptService.Server.Systems.Game`, and `src/game/client/Controllers` holds its client controllers (`FirstPersonCameraController`, `CutsceneController`, `FlashlightController`), mounted at `StarterPlayerScripts.Client.Controllers.Game`. `src/game/replicatedFirst/TeleportArrival.client.luau` is synced to `ReplicatedFirst` in both places and returns immediately outside the game place; in the game place it it parents the arriving teleport GUI into `PlayerGui` as `Teleporting_HUD` (or, when the player did not arrive by teleport, a clone of the Studio-owned `Teleporting_HUD` template from `ReplicatedFirst` or, failing that, `StarterGui`, started in the waiting state and tagged with the `ArrivalPhase` attribute) and removes the default loading screen.
- `Workspace.Cutscene_Camera`, `Workspace.Teleport_Players` (the `Player_1..5` R15 slot rigs), the sewer hole part (`Workspace.Cutscene_Hole`, or the first part named `Config.Cutscene.HoleName`, currently `PORTAL...Sewer.Main_Hole`), and the `Cutscene` ScreenGui (letterbox bars plus `Cutscene_Skip`, kept in `ReplicatedFirst` or `StarterGui`) are Studio-owned in the game place. `MatchSystem` publishes the cutscene inputs as `Workspace` attributes so they survive StreamingEnabled: `CutsceneCameraCFrame`/`CutsceneCameraFov` from the camera part (an optional `FieldOfView` attribute on it overrides `Config.Cutscene.FieldOfView`), `CutscenePlayersCFrame` (the slot group center), `CutsceneHoleCFrame`, `CutsceneSlot<i>` (each rig start pivot), and `CutsceneWalkEnd<i>` (where each rig stops: a single file line on the hole's center line, the slot nearest the hole first, head `Config.Cutscene.StopDistance` short of the hole and the rest `LineSpacing` apart behind it; the client keeps the starting formation until `LineMergeStart` of the walk and then blends into that line). It also pins the cutscene map for each arriving player: every `Model` under `Workspace.Cutscene_Map` (or, failing that, each entry of `Config.Cutscene.PinnedNames`: `Neighborhood`, `Teleport_Players`, `PORTAL`) is set to `PersistentPerPlayer`, the player is added on join and removed by `releaseCutsceneMap()` when their `CutsceneFinished` arrives; loose parts outside a `Model` cannot be pinned and are warned about. `GameSpawnSystem` anchors each rig root, assigns each arriving player a slot (the `SpawnSlot` player attribute), applies that player's `HumanoidDescription` to the slot rig (`ApplyDescription` rebuilds the limbs as new instances and can rescale the body, which silently breaks props and grounding: `dressRigAs` therefore records every `WeldConstraint` joining a rig body part to a prop model such as Player_1's phone, anchors the prop for the duration (`ApplyDescription` yields while it loads assets, and an unwelded prop is otherwise in free fall long enough to pass `FallenPartsDestroyHeight` and be deleted), then re-welds each prop to the rebuilt part afterwards, placing it from the limb's `*GripAttachment` when it has one so it sits in the hand on any avatar rather than at a fixed offset from the limb's centre, moves the rig's pivot back down to the feet (that pivot comes from `HumanoidRootPart.PivotOffset`, since `Model.WorldPivot` is ignored while a `PrimaryPart` is set), and pivots the rig to where it stood, so custom-proportioned avatars neither float nor drop the phone), destroys unused rigs when the match gate opens (or, in Studio with `Config.Cutscene.DebugFillSlots`, dresses them as stand-ins from `DebugFillUserIds` (entry `i` goes to slot `i`, so the list order is the slot order) and destroys them when the first character spawns), and only loads a player's character after that client sends `CutsceneFinished` or the cutscene timeout passes; that first character is dropped into the sewer: it is pivoted `Config.Cutscene.Landing.DropHeight` above the `SpawnLocation` inside `Workspace.Intro_Sewer` (`Landing.ModelName`), tilted by `TiltDegrees`, ragdolled on the server (engine `AnimationConstraint`s except `Root` and `<Joint>BallSocket`s disabled, then `WRagdoll:TurnRagdoll`) with the `Ragdolled` character attribute set, and after `RagdollSeconds` the server destroys the WRagdoll sockets and weld, re-enables the engine joints, and clears the attribute. `CutsceneController.finish()` puts the local humanoid into the `Physics` state (with a `TumbleSpeed` spin) while `Ragdolled` is set, and when it clears re-enables the `GettingUp` state (WRagdoll disables it), pivots the character upright `StandLift` studs above its resting spot facing the Studio-owned `Note_1` instance under `Workspace` (`Landing.FaceTargetName`, found recursively; a `Model` uses its pivot, a `BasePart` its position, and a missing target falls back to the way the ragdoll landed with a warning), and switches it to `GettingUp`. The landing is seen through the player's own eyes: once `Ragdolled` replicates (within `Landing.AttributeWaitSeconds`, otherwise the camera is handed straight over), the cutscene camera is unbound and `FirstPersonCameraController` is enabled while the dive's black fades away over `RevealSeconds`, so the fall plays from the ragdoll's head; after `BlackoutDelay` it fades back to black over `BlackoutSeconds`, and once `Ragdolled` clears (plus `WakeDelay`) the controller snaps behind the standing character's eyes and the black fades out over `WakeFadeSeconds` with a `WakeBlur` `BlurEffect` on the camera easing to zero, so the player wakes up already in first person. `FirstPersonCameraController` is the game place gameplay camera, tuned by `Config.Camera`: a Scriptable first-person camera bound after the engine camera, placed at the head's height measured in the root's frame (plus `EyeLift`, pushed `EyeForward` ahead and pulled back from walls by a raycast), the character's root turned to the camera yaw every frame, every character part and accessory hidden through `LocalTransparencyModifier` except the names in `VisibleParts` (the arms by default), and layered feel effects (stride head bob, strafe tilt, turn roll, noise breathing sway, a landing impact spring, and a speed FOV boost). While `Ragdolled` is set it instead rides the head's CFrame (smoothed by `RagdollViewSmoothing`) and ignores look input. Look input is `Config.Camera.Look`: mouse and touch are angle-per-pixel (`DegreesPerPixel`, `VerticalScale` for a flatter vertical axis, `Multiplier`), so they are frame-rate independent and the raw engine deltas are used as-is because the engine already applies the player's mouse sensitivity setting to them; the gamepad right stick is angle-per-second (`DegreesPerSecond` scaled by `dt`) through a per-axis `Deadzone` and exponential `Curve`, with `Acceleration` adding up to `Bonus` extra speed after the stick is held past `Threshold` for `RampSeconds`; `MaxDegreesPerFrame` caps any single frame's turn; look input is applied directly with no easing, so the view never lags the mouse. `StarterGui.MouseFrame` (the centre-screen `Crosshair` dot) is Studio-owned in the game place and must carry no script of its own: the controller toggles the ScreenGui's `Enabled` (found by `CrosshairGuiName`, re-found after respawns since it has `ResetOnSpawn`) so it shows only while the first-person camera is running on a non-ragdolled character and not suspended, and `setHudHidden()` keeps it off from `CutsceneController.start()` until `release()`, so it never appears during the intro cutscene, the fall, or the wake-up fade. It suspends itself while any of `SuspendAttributes` is set on the player. `CutsceneController.release()` always enables it, as does `start()` when no cutscene camera exists. `GameSpawnSystem.start()` anchors every loose part under the landing model and warns, because the Studio-owned `Intro_Sewer` model is currently unanchored and would otherwise fall out of the world at play start; anchor it in Studio. Later respawns use the Studio-owned `SpawnLocation` directly; if no landing spawn exists the character is placed at the slot's `CutsceneWalkEnd` instead. `CutsceneController` turns CoreGui off from start, holds the camera Scriptable at the camera part, pre-streams the camera, the slots, and the route to the hole every `Config.Cutscene.PreloadSpacing` studs, runs `ContentProvider:PreloadAsync` on the walk animation and the rig meshes/clothing, and sets the `CutscenePreloaded` player attribute, then once `ArrivalComplete` is set it shows the `Cutscene` GUI and runs the sequence: the rigs start walking locally at once while the camera cranes down onto the group from `PanDownLift`/`PanDownTiltDegrees` for `PanDownSeconds`, and the walk continues (pivoted from slot to `CutsceneWalkEnd` at `WalkSpeed` with the `WalkAnimationId` track) while the camera plays the `Config.Cutscene.Shots` list: each shot has a `startAt` walk fraction, `fov`, an `anchor` (`group` center or the `hole`), `from`/`to` offsets in the group's local frame (`{ forward, right, up }`) that dolly over the shot, a `focus` offset, and position `smoothing`; cuts are hard, FOV eases between shots, and `SwayAmount` adds a slight handheld drift. When the line has formed, the walkers keep walking straight into the hole: each rig is ragdolled locally: the client swaps the server-owned rig for a local clone (the client does not simulate physics on server-owned parts, even when unanchored locally), disables every engine joint on the clone (the game place rigs use the engine's Avatar Joint Upgrade, so that means every `AnimationConstraint` except `Root` plus the engine's `<Joint>BallSocket` constraints, whose friction the engine resets every frame and which are stiff enough to freeze the arms; a classic Motor6D rig has its motors disabled by the module), then runs `WRagdoll:TurnRagdoll` so the vendored module builds its own ball sockets from `src/vendor/WRagdoll/Joints.luau`; every part is then set non-colliding and unanchored so it drops through the road decal. Uniform free fall puts no load on any joint, so a ragdoll would hold its pose: only the torso gets the `TossSpeed`/`TossUp`/`TumbleSpeed` velocity, each limb gets a random `LimbScatter` kick and `LimbSpin` spin, and per-part `VectorForce`s (attachments named `CutsceneLift` on body parts only, never on accessory handles, since the Humanoid re-welds accessories to any part carrying a same-named attachment) cancel gravity down to `TorsoGravityScale` for the torso and `LimbGravityScale` for the limbs (the heavier torso plunges and flips while the limbs trail and swing); `release()` destroys the clones once it is `Config.Cutscene.Fall.DropDistance` short of the hole center, tossed forward with `TossSpeed`/`TossUp`/`Spread` and tumbled at `TumbleSpeed`, while the camera plays the `Config.Cutscene.Fall.Shots` list (same shape as `Shots`, anchored and focused on the hole, `startAt` measured over the approach); then `DiveDelay` after the last rig drops the camera rises from its last shot to `RiseHeight` above the hole center over `RiseSeconds` (turning to look down at the hole), plunges straight down to `DiveDepth` below it over `PlungeSeconds` (accelerating, looking at the falling bodies), and a client-created `CutsceneFade` ScreenGui goes black over the first `FadeDepth` studs below ground so the cut to black happens inside the hole; `release()` fades it back out over `FadeOutSeconds` once the character exists (`HoldSeconds` only applies when there is no hole). All cutscene audio is Studio-owned in `SoundService` and named through `Config.Cutscene.Audio`: `Forest_Music` (`MusicName`, the ambient bed) and `Intro_Cutscene_Music` (`CutsceneMusicName`, the score) both fade in over `MusicFadeInSeconds` when the sequence begins; the score fades out over `CutsceneMusicFadeOutSeconds` when the group reaches the hole and the drops begin, and every remaining track fades out over `MusicFadeOutSeconds` when the camera dive starts (or on release). Each rig that drops plays `Bone_Crack` (`BoneCrackName`, random `BoneCrackSpeedRange` pitch) and one of `ScreamNames` picked at random, both cloned onto that rig's root part so they are positional and follow the body down. `CinematicBoom2` (`BoomName`) fires `BoomLeadSeconds` before the camera crosses the hole's ground plane, to cover the asset's attack delay; the crossing time is solved from the dive geometry rather than sampled from the camera's height, which would otherwise fire at the start of the rise since the camera begins the dive below ground level. `Sewer_Sound_Effect` (`SewerSoundName`) plays once the landing character exists, and `Water_Splash` (`SplashName`) plays from the character's root the first time any of its torso or foot parts touches something outside itself, so it lands on the sewer floor impact. Cutscene footsteps pass `FootstepVolumeScale` to `FootstepsController.playStepAt` so they sit under the music; that third argument is optional and normal gameplay footsteps are unscaled. `Cutscene_Skip` is a shared vote rather than a personal skip: pressing it fires `CutsceneSkipVote`, `MatchSystem` counts one vote per player (a client's `CutsceneFinished` also counts, so a player whose cutscene already ended cannot block the rest) and broadcasts `CutsceneSkipState` with the tally over the number of players present, which `CutsceneController` writes into the button's votes label as `votes/total Votes` (found by its text containing "vote", else by a `number/number` pattern, since the Studio-owned button has two labels both named `TextLabel`). When every player has voted the server marks the vote complete and each client finishes. The fall end or a completed skip vote calls `CutsceneController.finish()`, which fires `CutsceneFinished`, waits for the character, and then `release()` hands the camera to `FirstPersonCameraController` and re-enables CoreGui.
- `Config.Places` in `src/shared/Modules/Config.luau` holds both place ids. `PartySystem` teleports each party to `Config.Party.GamePlaceId` in a reserved server with the party's difficulty, size, friends-only flag, and `memberIds` roster as teleport data, after waiting up to a few seconds for each client's `PartyTeleportReady` ack; `MatchSystem` reads that data on arrival, exposes it through `getSettings()`, and can send players back with `returnToLobby()`. `MatchSystem` also tracks the arrival roster, broadcasts `ArrivalState`, and opens the match gate (`isReady()`/`onReady()`) once everyone has arrived or `Config.Party.ArrivalTimeoutSeconds` passes, dropping missing players from the count; `GameSpawnSystem` waits on that gate, then on each client's `CutsceneFinished`, before loading characters.
- The flashlight is a game place item split between `src/game/server/Systems/FlashlightSystem.luau` and `src/game/client/Controllers/FlashlightController.luau`, tuned by `Config.Flashlight`, and it keeps the old game's split: other players see a handle welded to the character with the equip animation, while the local player sees only a camera-mounted viewmodel. Flashlight assets live in a Studio-owned folder named `Config.Flashlight.AssetFolder` (`Flashlight`) with `Server` and `Client` subfolders (`ServerFolder`/`ClientFolder`), found under `ReplicatedStorage.Assets` or anywhere under `ReplicatedStorage`. The client binds `ToggleKeys` (F and gamepad Y, plus a touch button titled `TouchButtonTitle`) through `ContextActionService` and fires `FlashlightToggle` with the wanted state (only while `FirstPersonCameraController` is enabled, the character is alive, and `Ragdolled` is not set, with a `ToggleCooldown` debounce). The server validates the same conditions, then clones the handle from `Server` (the first `Model` or `BasePart` named `ItemName`, else a `BasePart` named `HandleName` (`Handle`), else the first `Model`/`BasePart`; a `Model` is gripped by its authored `Motor6D`'s `Part1`, then its `Handle`, then its `PrimaryPart`; when nothing exists a plain part with a `SpotLight` is generated from `Config.Flashlight.Handle`/`Light`) into the character, tags it with the `FlashlightHandle` attribute, joins it to `RightHand` with a `Motor6D` named `GripName` (the asset's own `Motor6D` is reused with its authored C0/C1 and moved into the hand like the original script did, so the equip animation can drive it through the `Handle` part name; otherwise C0 comes from the hand's `RightGripAttachment` and C1 from the asset's `*GripAttachment`; in both cases `Config.Flashlight.Grip.Position`/`RotationDegrees` is multiplied onto C1), and plays `Flashlight_Equip` (an `Animation` named `Animations.EquipName` found in `Server`, the folder, or `Assets`, else `Animations.EquipId`) at `Animations.Priority`. The equip track is frozen (`AdjustSpeed(0)`) at the `HoldMarker` keyframe marker, or `HoldMargin` before its end when the animation has no marker, and at that moment every `Light`, `Beam`, `ParticleEmitter`, and `BillboardGui`/`SurfaceGui` under the handle (the old asset's `Attachment2.BOARD`) is enabled and the character's `FlashlightState` attribute goes from `Equipping` to `On`; turning off destroys the handle, sets `Unequipping` while `Item_Unequip` (`Animations.UnequipName`/`UnequipId`) plays at `UnequipSpeed`, then clears the attribute. Death, `Ragdolled`, the character being removed, or the player leaving end the session without the unequip animation. `SoundService.Flashlight_Click` (`Audio.ClickName`), or failing that a `Sound` named `Audio.AssetClickName` (`ON`) inside the flashlight folder, is cloned onto the root part on each on/off. The local player's `FlashlightController` hides every `FlashlightHandle`-tagged instance on its own character (parts through `LocalTransparencyModifier`, lights/beams/GUIs kept disabled) and, as soon as `FlashlightState` becomes `Equipping`, clones the `Client` subfolder's `Local.ItemName` (`Flashlight`) and `Local.NodeName` (`FlashNode`) parts under the camera: the item follows `Camera.CFrame * Offset` every frame, where `Offset` is its `Local.OffsetValueName` `Vector3Value` tweened from `HiddenOffset` to `ShownOffset` over `ShowSeconds` (Back easing) and back over `HideSeconds` before the item is destroyed; the node is re-tweened toward `Camera.CFrame * NodeOffset` every frame with a `NodeTweenSeconds` Back tween so its light lags and swings like the original; the item's `OnFx.OnUi` (`OnFxName`/`OnUiName`) is enabled while on, its `ON` sound (`Local.SoundName`) plays on each toggle, the node's lights are enabled while it exists, and an optional HUD image at `PlayerGui.MainUI.ItemUi.FlashlightOn` (`Local.HudPath`) fades in/out over `HudShowSeconds`/`HudHideSeconds` when present. Without a `FlashNode` asset a `SpotLight` part is generated from `Config.Flashlight.Light`; without a client `Flashlight` part only the node is shown and a warning is printed once.

## Luau Architecture

- Prefer ModuleScripts for game logic. Keep Scripts and LocalScripts as thin bootstraps.
- Server systems and client controllers expose `start()` and, when cleanup is needed, `stop()`.
- When adding a server system, require it in `src/server/Systems/SystemRegistry.luau` and add it to the lobby or game list. Order matters: `DataSystem` starts first and gameplay systems that read profiles come after it. Game-only systems live in `src/game/server/Systems`.
- When adding a client controller, require it in `src/client/Controllers/ControllerRegistry.luau` and add it to the lobby or game list. Game-only controllers live in `src/game/client/Controllers`.
- Before writing new logic, look for an existing module that owns the behavior and extend it instead of duplicating it.
- Guard repeated starts with an `isStarted` flag when the module owns connections, replicated state, or long-running tasks.
- Store `RBXScriptConnection` values and disconnect them in `stop()` or cleanup paths.
- Use `WaitForChild` for Rojo/replicated hierarchy dependencies that may not be immediately available.
- Keep server authority for persistence, economy, inventory, progression, and validation-sensitive behavior.
- Never trust client input. Validate player state, ownership, ranges, cooldowns, and amounts on the server.

## Data, Replication, and Networking

- Player persistence uses `ProfileStore` through `src/server/Modules/DataService.luau`, with the profile shape in `src/server/Modules/ProfileTemplate.luau`.
- Player data replication uses Replica (`src/vendor/Replica`). The client consumes the `PlayerData` replica through `src/client/Controllers/PlayerDataController.luau`.
- Keep data template changes backward-compatible and rely on reconcile paths for new fields.
- Sanitize currency and numeric state on the server before writing to profiles or replicas.
- Use Blink for all client-server gameplay networking. Never create raw `RemoteEvent` or `RemoteFunction` instances.
- Define new typed networking contracts in `src/network/main.blink`, regenerate with the pinned Blink tool, and commit the generated `src/shared/Blink` modules together with the IDL change.
- Do not manually edit generated Blink output.

## Style

- Follow the existing Luau style in this repo:
  - PascalCase for services, types, and module names.
  - camelCase for locals and parameters.
  - UPPER_SNAKE_CASE for constants.
  - Module tables returned at the bottom of the file.
  - Public module APIs and important data shapes should have Luau types.
- Do not add comments to any code you write in this project. (`src/replicatedFirst/Loading_Handler/init.client.luau` keeps its existing explanatory comments; leave them in place when editing it.)
- Keep source ASCII unless a file already uses non-ASCII or the asset/content requires it.
- Preserve existing instance names and casing in Rojo JSON files.

## Git Workflow

- `main` is the only long-lived branch for now. Branch feature work off `main` (`feature/<name>`) and merge back via PR or fast-forward.
- Commit messages are short imperative sentences (`Add player data service`).
- When the user explicitly asks to commit and/or push to GitHub, treat that as approval to stage the relevant changes, create a commit, and push to the configured remote without asking for additional confirmation.

## Before Finishing Work

- Check the worktree with `git status --short`.
- For script or project tree changes, run `& "$env:USERPROFILE\.rokit\tool-storage\rojo-rbx\rojo\7.7.0\rojo.exe" sourcemap default.project.json`.
- Run `git diff --check` before finishing code edits.
- If you changed Blink IDL, confirm the generated Blink client/server files are regenerated and committed with it.
- For behavior changes that depend on Roblox runtime behavior, verify in Studio when possible.
- Mention any commands that could not be run and why.
